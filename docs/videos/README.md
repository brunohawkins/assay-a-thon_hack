# Demo videos

One slot per **printed** demo chip, in [`manifest.json`](manifest.json). The slots, and what
to film in each (`shot`), are generated by `python tools/module_catalog.py` from the demo plan
when there is one, otherwise from the chip's protocol. Do not edit the slots by hand; the
`url`, `release_tag`, `recorded` and `duration_s` fields survive regeneration.

**Videos are not committed.** They live as assets of the GitHub Release tagged `demo-videos`.

## Recording

- **Phone on a stand**, straight down over the chip, locked focus and exposure. No hand-held.
- **Macro**: fill the frame with the 30 x 20 mm chip; a clip-on macro lens if the phone
  cannot focus that close. 1080p or 4K, 30 fps or more; landscape.
- **Ruler in shot**, flat beside the chip, millimetre marks visible, for scale.
- **Backlight**: a light pad or phone torch under a sheet of white paper below the chip, so
  dye fronts show against the channels. Kill overhead reflections.
- Food dye only, one colour per inlet. Nothing from the lab, no labels, no screens, no
  notebooks and no faces in frame.
- Say or caption the chip id (`module1_v1`, ...) at the start. Keep each take under 2 minutes;
  trim dead time rather than speeding up the flow.

## Publishing

```
gh auth login                                   # once, with write access to the repo
python tools/publish_video.py take.mp4 --module module1_v1             # dry run: says what it will do
python tools/publish_video.py take.mp4 --module module1_v1 --duration 75 --yes
```

It uploads the file to release `demo-videos` (creating it if missing) as `<chip_id>.mp4`,
writes the asset url into `manifest.json` and regenerates `docs/modules.md` /
`docs/modules.json`. Commit those two text files; never the video.

**Visibility.** Release assets of a PRIVATE repo are only visible to people with access to
the repo, so the url `publish_video.py` records is private. The Pages workflow downloads the
`demo-videos` assets at build time with its own token and serves them from the site's
`videos/` folder; the published manifest and `docs/modules.json` point there
(`videos/<chip_id>.mp4`, relative to the site root), and a slot with no downloaded file is
published with `url: null`. The videos are public only through the Pages site. In the
separate-public-repo fallback, upload with `--repo OWNER/PUBLIC_REPO` instead, or build with
`python tools/build_twin_site.py --videos DIR` after `gh release download demo-videos --dir DIR`.

## The public twin (GitHub Pages)

`.github/workflows/pages.yml` builds an allow-listed bundle with
`python tools/build_twin_site.py` (the twin, the data files it fetches, `docs/modules.json`;
it refuses to build if its confidentiality scan finds anything) and deploys it to Pages.
Nothing is switched on by the code:

1. **An admin must enable Pages**: Settings → Pages → Build and deployment → Source:
   **GitHub Actions**. Until then the deploy job fails and nothing is published.
2. **Pages from a PRIVATE repository needs a paid plan** (GitHub Pro, Team or Enterprise).
   On a free plan the option is not offered.
3. **Fallback** if Pages is not available on this repo: run
   `python tools/build_twin_site.py` and push the contents of `_site/` to a separate
   **public** repository, with Pages enabled there (source: the branch holding `_site/`).
   The repo with the code stays private.

Check exactly what would go public, with sizes, before any of that:
`python tools/build_twin_site.py --dry-run`.
